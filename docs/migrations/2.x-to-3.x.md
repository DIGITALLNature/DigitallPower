# Migrating from dgtp 2.x to 3.x

dgtp 3.0 replaces legacy profiles with typed connections and removes the combined top-level `push`
command. Use the resource-specific commands:

- `dgtp connection` for saved connections and authentication.
- `dgtp plugin push` for plugin assemblies and packages.
- `dgtp webresource push` for web resources.

This guide covers connection/profile migration and deployment changes. Review the 3.x release
notes for other changes that may affect your installation.

## Profiles and saved connections

The `profile` branch is removed, not retained as an alias. Use `connection` instead:

| Removed command | 3.x replacement |
|---|---|
| `profile list` | `connection list` |
| `profile create <name> <url> --msal` | `connection create <name> --url <url>` |
| `profile create <name> <connection-string>` | Recreate a typed connection using the authentication options below, or use a one-off connection string on the Dataverse command. |
| `profile select <name>` | `connection select <name>` |
| `profile delete <name>` | `connection delete <name>` |
| `profile purge` | `connection delete --all`; add `--yes` to skip confirmation in automation. |
| `profile auth-check` | `connection status` |

### Recreate connections after upgrading

**Existing 2.x profiles, saved connections, and cached sign-ins are not imported automatically.**
Before upgrading, record the environment URLs, connection names, and authentication settings you
need, keeping secrets in your existing secret manager. Recreate the connections in 3.x and sign
in again for user connections.

The new storage location is independent of the tool's major version. Saved connections live in
`connections.json` under the per-user dgtp data directory; `DGTP_HOME` can override that directory.
Client secrets and PFX passwords are stored separately using the platform's protected storage.
The old isolated-storage data is neither imported nor deleted; `connection delete --all` only
deletes the new saved connections and their associated credentials, not the legacy store.

Creation now uses typed authentication options instead of persisting an arbitrary connection string:

```powershell
# Interactive user sign-in; --tenant is optional
dgtp connection create dev --url https://contoso.crm4.dynamics.com

# User sign-in without a browser on the machine running dgtp
dgtp connection create dev-device --url https://contoso.crm4.dynamics.com --device-code

# Service principal; supply the secret through your secret-management tooling
dgtp connection create prod --url https://contoso.crm4.dynamics.com --tenant <tenant-id> --client-id <client-id> --client-secret <secret>

# Select the recreated connection and check authentication
dgtp connection select dev
dgtp connection status
```

Certificate and Azure DevOps federated connections are also supported. See the
[authentication type reference](../../README.md#authentication-types) for their setup requirements.
Client secrets and PFX passwords passed on the command line can be exposed in process arguments,
shell history, and pipeline logs; use secret masking and avoid echoing these commands.

Update existing creation scripts, including scripts already using the `connection` branch:

| Old option or behavior | 3.x replacement |
|---|---|
| Positional URL/connection string in `profile create` | Use `connection create <name> --url <url>` and the appropriate authentication options. |
| `profile create --msal` | Interactive sign-in is the default; use `--device-code` when needed. |
| `profile create --skipcheck` | Use `connection create --no-verify`. This skips the Dataverse connectivity check, not user sign-in. |
| `connection create --connection-string <string>` | Use typed authentication options, or supply the string to the Dataverse command without saving it. |
| `connection create --application-id <id>` for Azure DevOps federation | Use `--client-id <id>`. |
| `--insecure` / `--security-protocol` | Removed; configure certificate trust and TLS through the OS/runtime instead. |

`connection status` attempts token acquisition without interactive sign-in; it does not check
Dataverse permissions or connectivity. It returns `0` if a token is acquired (or an ad-hoc
connection-string check is skipped), and `2` if authentication is required or token acquisition
fails. `connection refresh` reauthenticates interactive/device-code connections only; it does not
rotate service-principal credentials.

### Invocation options and configuration

Replace `--profile <name>` with `--connection <name>` on Dataverse commands:

```powershell
dgtp export queues --connection dev --filedir ".\output"
```

Set `DGTP_CONNECTION` to select a named connection for an invocation, or use the saved selection
from `connection select`. For authentication modes or SDK options outside the saved types, pass
`--connection-string <string>` to the Dataverse command or set `DGTP_CONNECTION_STRING`. These
strings are never persisted. Prefer the environment variable for secret-bearing strings:

```powershell
# Populate this variable from your secret manager, not a committed script
$env:DGTP_CONNECTION_STRING = "<Dataverse connection string>"
dgtp export queues --filedir ".\output"
Remove-Item Env:\DGTP_CONNECTION_STRING
```

Command-line options override their corresponding environment variables. An ad-hoc connection
string takes precedence over a named connection, including one supplied with `--connection`.

The global `dgtp.json` configuration and `dgtp:*` environment-variable binding are removed:

| Legacy setting | 3.x replacement |
|---|---|
| `profile` / `dgtp:profile` | `--connection` / `DGTP_CONNECTION` |
| `xrm` connection-string settings / `dgtp:xrm:*` | Typed saved connections or `--connection-string` / `DGTP_CONNECTION_STRING` |
| `pollrate` (milliseconds) | `maintenance bulkdelete --poll-interval <seconds>`; default `5`, must be positive. |
| `DGT_TELEMETRY_OPTOUT` | `DGTP_TELEMETRY_OPTOUT` or `DO_NOT_TRACK` |

Command-specific configuration files remain supported. Review the
[current configuration reference](../../README.md#%EF%B8%8F-configuration) for supported environment
variables, including `DGTP_NON_INTERACTIVE` for unattended execution.

## Plugin deployments

Replace `dgtp push <assembly-or-package>` with `dgtp plugin push <assembly-or-package>`:

```bash
dgtp plugin push ./bin/Release/MyPlugin.dll --solution mysolution
dgtp plugin push ./bin/Release/MyPlugin.1.0.0.nupkg --publisher-prefix contoso --solution mysolution
```

Before migrating deployments, account for these differences:

- `plugin push` requires declarative registration attributes from
  `Digitall.Plugins.Registration` 3.0.0 or later. Historical registration namespaces are not
  recognized. Assemblies with manually maintained registrations must add supported attributes or
  continue deploying with dgtp 2.x.
- Workflow activities (`CodeActivity` / `WorkflowRegistrationAttribute`) are not supported by
  `plugin push`. Keep those deployments on dgtp 2.x until they have been replaced with a supported
  plugin or Custom API design.
- `--delete-on-upgrade` and `--no-migrate-custom-apis` are removed. For standalone assembly
  major/minor version changes, `plugin push` creates a replacement, migrates matching declared
  plugin steps, and removes the superseded assembly and registrations. Review the plan with
  `--dry-run` before deploying.
- `--publish` is not needed for plugin registration. Plugin registration takes effect immediately.
- `.nupkg` targets require `--publisher-prefix`; DLL-only targets do not.

`--confirm` prompts before applying each target plan in interactive sessions. Non-interactive and
CI runs do not prompt, so review the plan and deployment permissions before using the command in
automation.

### Custom data provider registrations

Data-provider deployment is still **experimental**. Validate the migration in a non-production
environment before production rollout.

Upgrade `Digitall.Plugins.Registration` to 3.0.0 or later, replace the removed entity-name constructor
with `(dataSourceSchemaName, eventRegistration, providerName)`, supplying the provider name on every
declaration, and rebuild the assembly. Use the configuration-table schema name, not
the business virtual-table name; changing this deployment key identifies a different provider.
See the [registration library](https://github.com/DIGITALLNature/DigitallRegistrationPower) for
attribute migration details and examples.

`plugin push` now deploys the provider and its configuration-table schema rather than ordinary
stage-30 SDK steps. Review and remove obsolete manually created stage-30 registrations separately;
they are not automatically deleted. See [deployment scope](../../README.md#custom-data-providers)
for what is and is not provisioned.

## Webresource deployments

Replace `dgtp push <directory>` with `dgtp webresource push <directory>`. For example:

```bash
dgtp webresource push ./webresources --publisher-prefix contoso --solution mysolution
```

The command options and validation differ from the combined command:

| 2.x behavior or option | 3.x behavior |
|---|---|
| `--config <file>` for webresource name mappings | Use `--mapping-file <file>`. |
| Derive directory names from the target solution | Pass `--publisher-prefix` explicitly for a directory target. |
| Push one webresource file by itself | Pass `--name <logical-name>`; `--publisher-prefix` is not needed for a single file. |
| `--publish` | Changed webresources are published automatically. |
| `--delete-obsolete` | Requires a directory target and `--solution`; an empty directory is a no-op and cannot delete every resource in the solution. |

The mapping file remains JSON. Mapping keys are paths relative to the target directory, and values
are Dataverse logical names. See the [webresource command documentation](../../README.md#webresource--manage-webresources)
for the complete option reference and mapping examples.

## Rollout checklist

1. Record the 2.x connections and authentication settings needed for your environments, then
   recreate and select typed connections in 3.x.
2. Replace `profile` commands, `--profile`, legacy creation options, and global configuration
   bindings in scripts and pipelines. Verify a non-production Dataverse command, not just
   `connection status`, before switching production automation.
3. Inventory scripts and pipelines that invoke `dgtp push`, including their target type and options,
   then move each deployment to its resource-specific command.
4. Identify workflow activities and assemblies without supported declarative registrations; these
   need a design change or must remain on dgtp 2.x.
5. Update option names and supply the required plugin package publisher prefix or webresource
   directory publisher prefix.
6. Run the replacement deployment commands with `--dry-run`, inspect the deployment plan, then
   validate in a non-production environment before switching production automation to 3.x.
7. Keep the approved dgtp 2.x version available for rollback until the migrated connections and
   deployments have been verified.
