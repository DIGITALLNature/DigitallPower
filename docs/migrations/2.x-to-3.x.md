# Migrating from dgtp 2.x to 3.x

dgtp 3.0 replaces legacy profiles with typed connections and removes the combined top-level `push`
command. Use the resource-specific commands:

- `dgtp connection` for saved connections and authentication.
- `dgtp plugin push` for plugin assemblies and packages.
- `dgtp webresource push` for web resources.
- `dgtp process init` and `dgtp process apply` for process state and ownership.
- `dgtp teamtemplates import` and `dgtp teamtemplates export` for team templates.
- `dgtp documenttemplates import` and `dgtp documenttemplates export` for Word/Excel templates.

This guide covers connection/profile migration, retired legacy transfers, process management, document templates and deployment changes. Review the 3.x release
notes for other changes that may affect your installation.

## Retired legacy transfers

The top-level `import` and `export` branches, their `dgt.power.import` and `dgt.power.export`
assemblies, and their command/settings/base types are removed without compatibility aliases.
Update scripts: the following paths now fail parsing with an unknown-command diagnostic and a
nonzero exit code before resolving a Dataverse service.

| Removed import path | Removed export path | Unsupported legacy JSON contract | 3.x replacement |
|---|---|---|---|
| `import bulkdeletes` | `export bulkdeletes` | `bulkdelete.json`: recurring job definitions, schedules and disable flags | None |
| `import queues` | `export queues` | `queue.json`: queue settings and ownership | None |
| `import calendar` | `export calendars` | `calendar.json`: service/holiday calendars and nested rules | None |
| `import slaconfigs` | `export slaconfigs` | `slaconfig.json`: existing SLA calendar, ownership and state | None |
| `import routingruleconfigs` | `export routingruleconfigs` | `routingruleconfig.json`: existing rule ownership, state and targets | None |
| `import userroles` | `export userroles` | `userrole.json`: direct role assignments and business-unit synchronization | None |
| `import outlooktemplates` | `export outlooktemplates` | `outlooktemplate.json`: Outlook synchronization-filter defaults and FetchXML | None |

Neither replacement commands nor supported configuration migrations are provided for any of these
seven pairs, including custom filenames holding the same legacy formats. No exact PAC equivalent
is promised for their synchronization behavior or JSON contracts. Outlook synchronization filters
are not Word/Excel document templates.

Retiring the CLI does not modify existing Dataverse jobs, queues, calendars, SLAs, routing rules,
user-role assignments, or Outlook filters. Existing recurring bulk-delete jobs are not cancelled,
disabled, or deleted; review them separately if their schedules need changing. One-off
`maintenance bulkdelete` execution is owned by the separate maintenance-retirement change, not
a replacement for recurring-job transfer.

The exclusive legacy DTOs are also removed: `dgt.power.dto.Assignee`, `BulkDelete`, `BulkDeletes`,
`Calendar`, `CalendarRule`, `OutlookTemplate`, `Queue`, `Queues`, `RoutingRuleConfig`, `SavedQuery`,
`SlaConfig`, `UserRole`, and `dgt.power.common.DTO.RoutingRuleItem`. Consumers of these public
types must remove those integrations; no supported replacement data contract is provided.

The independently migrated `teamtemplates import/export` and `documenttemplates import/export`
commands remain available with their resource-owned V1 contracts (see below). The already retired
`import secureconfigs` path remains rejected; use `plugin step config set` for secure plugin-step
configuration.

## Team template transfer

The verb-first team-template commands have been removed without aliases:

| Removed command | 3.x replacement |
|---|---|
| `export teamtemplates` | `teamtemplates export <File>` |
| `import teamtemplates` | `teamtemplates import <File>` |

The old transfer file was a bare JSON list and could include system templates. First discard
all entries marked `issystem: true`; their GUIDs are protected, and including them would cause
the entire import to fail preflight. Then remove the `issystem` property from the remaining
entries and wrap them in the versioned V1 envelope. Preserve each remaining template GUID and
logical table name and supply a valid access-rights mask:

```json
{
  "$schema": "https://raw.githubusercontent.com/DIGITALLNature/DigitallPower/main/schemas/teamtemplates/v1/schema.json",
  "schemaVersion": 1,
  "templates": [
    {
      "teamtemplateid": "4e17461c-efec-43a0-835b-08fa78af1f83",
      "entity": "account",
      "teamtemplatename": "Account readers",
      "description": null,
      "defaultaccessrightsmask": 1
    }
  ]
}
```

`defaultaccessrightsmask` is required and must be a non-zero combination of supported access-team
rights: Read (`1`), Write (`2`), Append (`4`), Append To (`16`), Delete (`65536`), Share
(`262144`), and Assign (`524288`). Create (`32`) is not supported. Names are limited to 100
characters, descriptions to 1,500 characters, and table names must match
`^[a-z][a-z0-9_]*$`. Name duplicates and target collisions are case-insensitive. The legacy bare
array is not read automatically.

Import matches by GUID only. It never adopts a same-name record with a different GUID, and an
existing GUID cannot be reassigned to another table. Conflicts, system-template targets, invalid
rights, and invalid table metadata fail preflight before any writes. Omitted or null descriptions
clear the existing description. Unlisted templates remain unchanged by default.

Use `--overwrite` to replace an existing export file. Export selection uses repeatable
`--table <LogicalName>` options. Cleanup is also opt-in: pass both `--cleanup` and one or more
repeatable `--cleanup-table <LogicalName>` options. Cleanup scope is never inferred from the file
or export filters; there is no `--all` or other global cleanup option. System templates are
protected, and an empty input with cleanup is rejected.
Both commands support `--dry-run`; import validates the full plan but does not write, while export
does not create or replace its file. Import is not transactional: mutations stop at the first
failure, completed work is not rolled back, and cleanup starts only after all creates and updates
succeed.

## Process state and ownership

The legacy workflow-state commands, configuration reader and schema are removed without aliases:

| Removed command | 3.x replacement |
|---|---|
| `maintenance createworkflowstate --output <File> --solutions <Names>` | `process init <File> --solution <UniqueName>`; repeat `--solution` instead of passing comma-separated names |
| `maintenance workflowstate --config <File>` | `process apply <File>` |

Regenerate configuration rather than renaming old properties:

```bash
dgtp process init ./processes.json --solution ContosoCore \
  --capture both --owner-mapping ./owners.source.json
dgtp process apply ./processes.json --owner-mapping ./owners.target.json --dry-run
dgtp process apply ./processes.json --owner-mapping ./owners.target.json
```

Use `--overwrite` explicitly when recapturing an existing file. The new V1 format uses
`schemaVersion: 1` and a `processes` array with a nonempty `processId` GUID and at least one of
`active` or `owner` per entry. See the [process command reference](../../README.md#process--process-state-and-ownership)
and [V1 schema](../../schemas/process/v1/schema.json).

| Legacy behavior or setting | 3.x behavior |
|---|---|
| Display-name, unique-name or table-scoped keys | `workflowid` is the only identity (`processId`); optional `name` is ignored for matching. Processes recreated under different IDs require explicit configuration changes. |
| `disabled` flags | Explicit `active` booleans; invert existing intent when migrating. Omitted state is preserved, not activated implicitly. |
| `defaultOwner`, per-process domain names | Environment-specific portable owner mappings and explicit logical-key `owner`; no most-common-owner default. Regular and application users are supported, not teams. |
| `defaultImpersonate` or per-flow impersonation | Run-level `--activate-as <OwnerKey>` or `--activate-as-owner`, mutually exclusive. These apply to both activation and deactivation; assignments use the connection identity. Caller acquisition failure never falls back to that identity. |
| `--solutions`, `solutionFilter` | Required repeatable exact `--solution` on init only; apply acts exclusively on configured IDs. |
| Publisher, wildcard or managed-state selection | Not supported. Capture exact solutions and edit explicit intent instead. |
| `--tablereport`, `--detailed` | Removed; outcomes are always reported. |
| `schemas/maintenance/workflow/schema.json` | `schemas/process/v1/schema.json`; no legacy-format reader. |

Classic workflows, business rules, actions, business process flows and cloud flows are supported.
Dialogs, AI flows and desktop flows are not. Capture includes indirect business rules only for
tables included with all subcomponents. Definitions and connection references are not deployed.

Review the generated file before applying it. Unlisted processes and omitted properties are
preserved. Owner-only changes preserve activation state through any required intermediate
deactivation. Preflight resolves the full input before writes, but execution is not atomic:
independent updates continue after failures, requested activations may be retried, and a failed
assignment after deactivation triggers one restoration attempt. Inspect the report for partial
effects and unrecovered inactive processes. Dry-run does not prove privileges or activation
dependencies.

Consumers referencing the removed public maintenance types (`CreateWorkflowStateConfig`,
`CreateWorkflowStateConfigSettings`, `UpdateWorkflowState`, `UpdateWorkflowStateSettings`,
`WorkflowConfig`, `WorkflowBaseConfig`, `WorkflowFlowConfig`, `WorkflowStateManager` and
`WorkflowStateTracker`) must migrate to the resource-owned process commands and V1 contract.

## Document templates

The old documenttemplate commands and DTOs are removed without aliases:

| Removed command | Replacement |
|---|---|
| `import documenttemplates --filedir <Directory> --filename <File>` | `documenttemplates import <Manifest> [--dry-run]` |
| `export documenttemplates --filedir <Directory>` | `documenttemplates export <Directory> [--entity <LogicalName>] [--type word\|excel] [--overwrite]` |

Regenerate packages using the new export command rather than relabeling a legacy manifest.
V1 requires `schemaVersion: 1` and `templates`; each entry requires `sourceId`, `name`,
`documentType` (`word` or `excel`), `entity`, `file`, `languageCode` and `description`
(string or explicit null). Legacy `document_status`, `force_update`, `ignore_missing`,
snake-case metadata properties, FetchXML inline filters and `FORCE`/`MISSING` directives
are not parsed. The removed `dgt.power.dto.DocumentTemplate` and `DocumentTemplates` types
are replaced by resource-owned manifest models.

```bash
dgtp documenttemplates export ./templates --entity account
dgtp documenttemplates import ./templates/documenttemplates.json --dry-run
dgtp documenttemplates import ./templates/documenttemplates.json
```

Matching now uses `(name, documentType, entity)` with case-insensitive names. A match preserves
its target ID, while a new template uses `sourceId`; conflicting IDs fail preflight. Names are
not trimmed and extensions are not stripped. Changed identity components do not infer renames.
Documents must remain inside the manifest directory, including symlink resolution; search-path
fallbacks are removed. Explicit null descriptions clear the target and language has no default.

Export includes active templates only; import activates every successfully listed template.
This is active deployment, not draft-preserving backup/restore. Unlisted templates stay unchanged.
No cleanup, implicit deactivation, forced replacement or delete/recreate is available.
Preparation precedes all writes, but execution is best-effort and can leave reported partial
effects. Unknown Word bindings/relationships fail validation instead of being silently skipped.
Only the explicitly evidenced account/lead legacy N:N aliases are supported; other unknown
legacy aliases require review. Excel content is uploaded without client adaptation.

See the [documenttemplate guide](../../README.md#documenttemplates--portable-document-templates)
and [V1 schema](../../schemas/documenttemplates/v1/schema.json).

## Code generation

dgtp 3 supports explicitly versioned V2 code-generation configs only. Unversioned and V1 configs
are rejected; adding `version: 2` and `type` to a V1 file is not a complete migration. V2 uses one
config and invocation per target. The discriminator property and value are case-sensitive: use
lowercase `"type"` with `"dotnet"` or `"typescript"`. It may appear anywhere in the JSON object;
`$schema` annotations remain supported.

For example, this combined V1 config must be split rather than relabeled:

```json
{
  "version": 1,
  "Entities": ["account", "contact"],
  "Solutions": ["ContosoCore"],
  "Actions": ["contoso_ApproveOrder"],
  "GlobalOptionSets": ["contoso_status"],
  "NameSpace": "Contoso.Dataverse.Model",
  "SuppressTypeScript": true
}
```

```json
{
  "$schema": "https://raw.githubusercontent.com/DIGITALLNature/DigitallPower/main/schemas/codegeneration/v2/dotnet.schema.json",
  "version": 2,
  "type": "dotnet",
  "namespace": "Contoso.Dataverse.Model",
  "entities": { "names": ["account", "contact"], "fromSolutions": ["ContosoCore"] },
  "requests": ["contoso_ApproveOrder"],
  "optionSets": ["contoso_status"],
  "output": { "include": { "metadata": true } }
}
```

```json
{
  "$schema": "https://raw.githubusercontent.com/DIGITALLNature/DigitallPower/main/schemas/codegeneration/v2/typescript.schema.json",
  "version": 2,
  "type": "typescript",
  "entities": { "names": ["account", "contact"], "fromSolutions": ["ContosoCore"] },
  "requests": ["contoso_ApproveOrder"],
  "optionSets": ["contoso_status"]
}
```

Run each target separately, using the corresponding config file:

```powershell
dgtp codegeneration ./generated -c ./genconfig.dotnet.json
dgtp codegeneration ./generated -c ./genconfig.typescript.json
```

Common V1 fields map into the typed V2 scope and output settings as follows:

| V1 field or behavior | V2 migration |
|---|---|
| `Entities`, `Solutions`, `EntityMask` | `entities.names`, `entities.fromSolutions`, `entities.mask` |
| `Actions`, `CustomAPIs`, `AdditionalSdkMessages`, `SdkMessageFilters` | Put the request names to generate in `requests`; V2 has no separate SDK-message filter. |
| `GlobalOptionSets` | `optionSets` |
| `NameSpace`, `UseBaseLanguage` | Set `namespace` explicitly for .NET; the V1 default was `Digitall.APower.Model`, while typed V2 configs use `Digitall.Dataverse.Model` by default (this changed in dgtp 2.1). The TypeScript `namespace` field is accepted but currently unused. Set `language` to an LCID when needed; `language: null` uses the organization base language. |
| `Forms` | `output.forms.filter` in the TypeScript config, using the V2 form identifier format. |
| `SuppressOptions`, `SuppressLogicalNames`, `SuppressContext`, `SuppressRelations`, `SuppressNavigationProperties`, `SuppressEntityTypeCode`, `SuppressAlternateKeys` | For .NET, set the matching `output.include` property to the inverse boolean, for example `SuppressContext: true` becomes `output.include.context: false`. For TypeScript, select the option sets to generate through `optionSets`; it has no V1-style output suppression flag. |
| `SuppressActions` | Remove Custom API/action names from `requests` to omit their wrappers and requested message constants. For TypeScript, `output.customApis: false` disables wrappers while retaining requested message declarations. .NET has no independent wrapper-suppression switch. |
| `SuppressSdkMessages` | No independent V2 equivalent. .NET always emits SDK message constants, including built-ins, even when `requests` is empty. TypeScript omits message declarations when `requests` is empty, but removing Custom API names also removes their wrappers. |
| `SuppressMetaData` | Invert to `output.include.metadata`. Note the default changes: V1 generated metadata when this flag was omitted, while V2 defaults metadata off. Set `output.include.metadata: true` when that output is still required. |
| `SuppressDotNet`, `SuppressTypeScript` | Select which target config(s) to create and invoke; there is no combined generation command. |
| `Virtual`, `EditableReadOnlyProperties`, `OnlyFormsFromSolutions`, `XrmMockFormHelpers` | `output.virtual`, `output.editableReadOnly`, `output.forms.fromSolutions`, `output.forms.testHelpers` in the relevant target config. |
| `SuppressNullableSupport` | Select the .NET target that matches the intended nullable behavior; V2 does not have a separate nullable-suppression switch. |

V1 `TypescriptGeneratorVersion: "Full"` is removed. Update TypeScript consumers that depend on
Full-only runtime entity or form-context wrappers to use the supported ambient/interface output.
The former Light output is the single supported TypeScript pipeline; there is no mode selector.
`EntityFilters`, `EntityRefFilters`, and `EntityFormFilters` are rejected and have no replacement.
Review any use of other V1-only settings, such as `Hints`, `TypingPath`, or
`BusinessProcessFlows`; V2 has no equivalent field for them.

Code that references the code-generation module API directly must replace the V1
`CodeGenerationConfig`/`CodeGenerationConfigResult` path and legacy metadata overloads with
`DotNetCodeGenerationConfig` or `TypeScriptCodeGenerationConfig` and the typed generator contracts.
The V1 filter model types and `TypescriptGeneratorVersion` are also removed. The `codegeneration`
command, its `cg` alias, and its options remain unchanged. Code using the removed
`CodeGenerationConfigFactory.ResolveFromFile` API should load configs through
`CodeGenerationConfigLoader.LoadFromFile`, which returns the typed base config and uses the standard
JSON discriminator contract.

Before regenerating, back up any custom edits inside generated folders. TypeScript generation
clears the entire `Model/TypeScript` subtree, which includes the old Full-mode files (`model.ts`,
`services.ts`, `webapi.ts`, `utils.ts`, `odata.ts`, entity-reference declarations, and BPF output).
.NET generation deletes generated `*.cs` files directly inside `Model/DotNet`; metadata generation
deletes `*.xml` files directly inside `Model/MetaData`. Files outside those existing cleanup
boundaries are not removed automatically; inspect and remove obsolete generated files there yourself.

## Profiles and saved connections

The `profile` branch is removed, not retained as an alias. Use `connection` instead:

| Removed command | 3.x replacement |
|---|---|
| `profile list` | `connection list` |
| `profile create <name> <url> --msal` | `connection create <name> --url <url>` |
| `profile create <name> <connection-string>` | Recreate a typed connection using the authentication options below, or use a one-off connection string on the Dataverse command. |
| `profile select <name>` | `connection select <name>` |
| `profile delete <name>` | `connection delete <name>` |
| `profile purge` | `connection delete --all`; add `--yes` to skip confirmation in automation. |
| `profile auth-check` | `connection status` |

### Recreate connections after upgrading

**Existing 2.x profiles, saved connections, and cached sign-ins are not imported automatically.**
Before upgrading, record the environment URLs, connection names, and authentication settings you
need, keeping secrets in your existing secret manager. Recreate the connections in 3.x and sign
in again for user connections.

The new storage location is independent of the tool's major version. Saved connections live in
`connections.json` under the per-user dgtp data directory; `DGTP_HOME` can override that directory.
Client secrets and PFX passwords are stored separately using the platform's protected storage.
The old isolated-storage data is neither imported nor deleted; `connection delete --all` only
deletes the new saved connections and their associated credentials, not the legacy store.

Application state also moves to the stable data directory as `state.json`. The 2.x telemetry
identity, notice state, and update-check timestamp are not imported. A new anonymous installation
ID and one-time telemetry notice are initialized on the first telemetry-enabled command in 3.x.
`DGTP_TELEMETRY_OPTOUT`, `DO_NOT_TRACK`, and `--no-telemetry` suppress this initialization.
Future tool upgrades reuse this state independently of the application major version.

Creation now uses typed authentication options instead of persisting an arbitrary connection string:

```powershell
# Interactive user sign-in; --tenant is optional
dgtp connection create dev --url https://contoso.crm4.dynamics.com

# User sign-in without a browser on the machine running dgtp
dgtp connection create dev-device --url https://contoso.crm4.dynamics.com --device-code

# Service principal; supply the secret through your secret-management tooling
dgtp connection create prod --url https://contoso.crm4.dynamics.com --tenant <tenant-id> --client-id <client-id> --client-secret <secret>

# Select the recreated connection and check authentication
dgtp connection select dev
dgtp connection status
```

Certificate and Azure DevOps federated connections are also supported. See the
[authentication type reference](../../README.md#authentication-types) for their setup requirements.
Client secrets and PFX passwords passed on the command line can be exposed in process arguments,
shell history, and pipeline logs; use secret masking and avoid echoing these commands.

Update existing creation scripts, including scripts already using the `connection` branch:

| Old option or behavior | 3.x replacement |
|---|---|
| Positional URL/connection string in `profile create` | Use `connection create <name> --url <url>` and the appropriate authentication options. |
| `profile create --msal` | Interactive sign-in is the default; use `--device-code` when needed. |
| `profile create --skipcheck` | Use `connection create --no-verify`. This skips the Dataverse connectivity check, not user sign-in. |
| `connection create --connection-string <string>` | Use typed authentication options, or supply the string to the Dataverse command without saving it. |
| `connection create --application-id <id>` for Azure DevOps federation | Use `--client-id <id>`. |
| `--insecure` / `--security-protocol` | Removed; configure certificate trust and TLS through the OS/runtime instead. |

`connection status` attempts token acquisition without interactive sign-in; it does not check
Dataverse permissions or connectivity. It returns `0` if a token is acquired (or an ad-hoc
connection-string check is skipped), and `2` if authentication is required or token acquisition
fails. `connection refresh` reauthenticates interactive/device-code connections only; it does not
rotate service-principal credentials.

### Invocation options and configuration

Replace `--profile <name>` with `--connection <name>` on Dataverse commands:

```powershell
dgtp export queues --connection dev --filedir ".\output"
```

Set `DGTP_CONNECTION` to select a named connection for an invocation, or use the saved selection
from `connection select`. For authentication modes or SDK options outside the saved types, pass
`--connection-string <string>` to the Dataverse command or set `DGTP_CONNECTION_STRING`. These
strings are never persisted. Prefer the environment variable for secret-bearing strings:

```powershell
# Populate this variable from your secret manager, not a committed script
$env:DGTP_CONNECTION_STRING = "<Dataverse connection string>"
dgtp export queues --filedir ".\output"
Remove-Item Env:\DGTP_CONNECTION_STRING
```

Command-line options override their corresponding environment variables. An ad-hoc connection
string takes precedence over a named connection, including one supplied with `--connection`.

The global `dgtp.json` configuration and `dgtp:*` environment-variable binding are removed:

| Legacy setting | 3.x replacement |
|---|---|
| `profile` / `dgtp:profile` | `--connection` / `DGTP_CONNECTION` |
| `xrm` connection-string settings / `dgtp:xrm:*` | Typed saved connections or `--connection-string` / `DGTP_CONNECTION_STRING` |
| `pollrate` (milliseconds) | `maintenance bulkdelete --poll-interval <seconds>`; default `5`, must be positive. |
| `DGT_TELEMETRY_OPTOUT` | `DGTP_TELEMETRY_OPTOUT` or `DO_NOT_TRACK` |

Command-specific configuration files remain supported. Review the
[current configuration reference](../../README.md#%EF%B8%8F-configuration) for supported environment
variables, including `DGTP_NON_INTERACTIVE` for unattended execution.

## Custom Dataverse connection implementations

`IDataverseConnection` now also requires
`Task<IOrganizationServiceAsync2> GetServiceAsync(Guid callerId)`. Custom implementations must
reject `Guid.Empty` before authentication and return an isolated, ready service configured for
the specified Dataverse `systemuser` ID, or explicitly throw `NotSupportedException`. Never
ignore the ID or return the standard service as a fallback.

The connection owns and disposes its standard and caller services. Consumers borrow services
without disposal or caller-state mutation. Successful acquisition does not validate caller
existence, enabled status, or operation privileges; see the
[caller-service contract](../../README.md#caller-specific-dataverse-services).

## Plugin deployments

Replace `dgtp push <assembly-or-package>` with `dgtp plugin push <assembly-or-package>`:

```bash
dgtp plugin push ./bin/Release/MyPlugin.dll --solution mysolution
dgtp plugin push ./bin/Release/MyPlugin.1.0.0.nupkg --publisher-prefix contoso --solution mysolution
```

Before migrating deployments, account for these differences:

- `plugin push` requires declarative registration attributes from
  `Digitall.Plugins.Registration` 3.0.0 or later. Historical registration namespaces are not
  recognized. Assemblies with manually maintained registrations must add supported attributes or
  continue deploying with dgtp 2.x.
- Workflow activities (`CodeActivity` / `WorkflowRegistrationAttribute`) are not supported by
  `plugin push`. Keep those deployments on dgtp 2.x until they have been replaced with a supported
  plugin or Custom API design.
- `--delete-on-upgrade` and `--no-migrate-custom-apis` are removed. For standalone assembly
  major/minor version changes, `plugin push` creates a replacement, migrates matching declared
  plugin steps, and removes the superseded assembly and registrations. Review the plan with
  `--dry-run` before deploying.
- `--publish` is not needed for plugin registration. Plugin registration takes effect immediately.
- `.nupkg` targets require `--publisher-prefix`; DLL-only targets do not.
- The target may also be a glob pattern. The whole batch is validated before any write, so
  duplicate assembly, package, data provider or Custom API declarations across targets and
  unreadable artifacts fail the run. A target matching no files, or files without plugins, fails
  the run.

`--confirm` prompts before applying each target plan in interactive sessions. Non-interactive and
CI runs do not prompt, so review the plan and deployment permissions before using the command in
automation.

### Custom data provider registrations

Data-provider deployment has **experimental support**. Validate the migration in a non-production
environment before production rollout.

Upgrade `Digitall.Plugins.Registration` to 3.0.0 or later, replace the removed entity-name constructor
with `(dataSourceSchemaName, eventRegistration, providerName)`, supplying the provider name on every
declaration, and rebuild the assembly. Use the configuration-table schema name, not
the business virtual-table name; changing this deployment key identifies a different provider.
See the [registration library](https://github.com/DIGITALLNature/DigitallRegistrationPower) for
attribute migration details and examples.

`plugin push` now deploys the provider record rather than ordinary stage-30 SDK steps. The
configuration table must already exist in the target environment; it is not created or added to
the solution. Review and remove obsolete manually created stage-30 registrations separately;
they are not automatically deleted. See [deployment scope](../../README.md#custom-data-providers)
for what is and is not provisioned.

### Plugin step configuration

`import secureconfigs` is removed. The legacy JSON identified a plugin step by its display name
in `plugin_step` and supplied its secure value through `secure_config`:

```json
{
  "plugin_step": "<plugin step display name>",
  "secure_config": "<secret value>"
}
```

There is no automatic conversion or import-compatible adapter. In the target environment, use the
Dataverse step ID or resolve the step to the complete composite key (`--plugin-type`, `--message`,
`--stage`, and `--entity`). Do not assume a display name uniquely identifies a step.
There is no bulk, one-to-one replacement for importing secure configurations: configure each
plugin step individually with `plugin step config set`. If you need to configure multiple steps,
write and run your own script to invoke the command for each step.

For a file-based value, put only the secure configuration text—not the old JSON envelope—in the
file, then run:

```powershell
dgtp plugin step config set --step-id <step-guid> --secure-file .\secure-value.txt
```

Alternatively, select the step by composite key or supply an inline value:

```powershell
dgtp plugin step config set --plugin-type Contoso.Plugins.Sample --message Update --stage PreOperation --entity account --secure-file .\secure-value.txt
dgtp plugin step config set --step-id <step-guid> --secure "<value-from-secret-manager>"
```

`--secure ""` explicitly clears the secure configuration; omitting `--secure` and
`--secure-file` leaves it unchanged. The equivalent unsecure options are `--unsecure` and
`--unsecure-file`. Inline values may be exposed in process arguments, shell history, or logs;
prefer a protected secret file and avoid committing either the file or its contents. The legacy
`--filedir`, `--filename`, and `--inline` import inputs do not apply to `plugin step config set`.

### Managed identities

`plugin push` does not provision or bind managed identities. Remove
`ManagedIdentityRegistrationAttribute` declarations from plugin assemblies. Configure the
Dataverse identity record, assembly/package binding, Entra federated credential, and permissions
through each environment's provisioning pipeline instead.

Existing target bindings remain untouched during updates. New standalone replacement assemblies
do not inherit the superseded assembly's binding and need separate provisioning. The same signed
artifact can be promoted across environments with different app registrations or user-assigned
managed identities; federation trust includes the environment ID.

## Webresource deployments

Replace `dgtp push <directory>` with `dgtp webresource push <directory>`. For example:

```bash
dgtp webresource push ./webresources --publisher-prefix contoso --solution mysolution
```

The command options and validation differ from the combined command:

| 2.x behavior or option | 3.x behavior |
|---|---|
| `--config <file>` for webresource name mappings | Use `--mapping-file <file>`. |
| Derive directory names from the target solution | Pass `--publisher-prefix` explicitly for a directory target. |
| Push one webresource file by itself | Pass `--name <logical-name>`; `--publisher-prefix` is not needed for a single file. |
| `--publish` | Changed webresources are published automatically. |
| `--delete-obsolete` | Requires a directory target and `--solution`; an empty directory is a no-op and cannot delete every resource in the solution. |

The mapping file remains JSON. Mapping keys are paths relative to the target directory, and values
are Dataverse logical names. See the [webresource command documentation](../../README.md#webresource--manage-webresources)
for the complete option reference and mapping examples.

## Rollout checklist

1. Record the 2.x connections and authentication settings needed for your environments, then
   recreate and select typed connections in 3.x.
2. Replace `profile` commands, `--profile`, legacy creation options, and global configuration
   bindings in scripts and pipelines. Verify a non-production Dataverse command, not just
   `connection status`, before switching production automation.
3. Inventory scripts and pipelines that invoke `dgtp push`, including their target type and options,
   then move each deployment to its resource-specific command.
4. Identify workflow activities and assemblies without supported declarative registrations; these
   need a design change or must remain on dgtp 2.x.
5. Update option names and supply the required plugin package publisher prefix or webresource
   directory publisher prefix.
6. Run the replacement deployment commands with `--dry-run`, inspect the deployment plan, then
   validate in a non-production environment before switching production automation to 3.x.
7. Keep the approved dgtp 2.x version available for rollback until the migrated connections and
   deployments have been verified.

## Plugin step management

The maintenance command `ensuresdksteps` has been removed. Use the plugin step commands with the
`--solution` parameter instead:

```bash
# Enable all steps in a solution
dgtp plugin step enable --solution mysolution

# Disable all steps in a solution
dgtp plugin step disable --solution mysolution
```

The new commands support three mutually exclusive identification modes:

- By step ID: `--step-id <guid>`
- By composite key: `--plugin-type <type> --message <msg> --stage <stage> --entity <entity>`
- By solution: `--solution <name>` (applies to ALL steps in the solution)

Differences from `ensuresdksteps`:

- `--dry-run` is supported; there is no `--confirm` option.
- Steps already in the desired state are skipped and reported as unchanged.
- The solution name is matched exactly (no wildcard matching); an unknown solution fails.
- `--reason` replaces the step description, and only when the state changes.
