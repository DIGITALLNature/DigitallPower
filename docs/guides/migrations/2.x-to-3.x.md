# Migrating from dgtp 2.x to 3.x

dgtp 3.0 replaces legacy profiles with typed saved connections and removes the combined top-level
`push` command, the legacy `import`/`export` transfers, the `maintenance` branch, and the `analyze`
branch. This guide lists the user-facing breaking changes and what to do about them. Review the
3.x release notes for other changes that may affect your installation.

The resource-specific commands that replace `push` and the retired transfers:

- `dgtp connection` for saved connections and authentication.
- `dgtp plugin push` for plugin assemblies and packages.
- `dgtp webresource push` for web resources.
- `dgtp process init` and `dgtp process apply` for process state and ownership.
- `dgtp teamtemplates import` and `dgtp teamtemplates export` for team templates.
- `dgtp documenttemplates import` and `dgtp documenttemplates export` for Word/Excel templates.

## Retired legacy transfers

The top-level `import` and `export` branches are removed without compatibility aliases. The
following paths now fail with an unknown-command diagnostic and a nonzero exit code:

| Removed import path | Removed export path | 3.x replacement |
|---|---|---|
| `import bulkdeletes` | `export bulkdeletes` | None |
| `import queues` | `export queues` | None |
| `import calendar` | `export calendars` | None |
| `import slaconfigs` | `export slaconfigs` | None |
| `import routingruleconfigs` | `export routingruleconfigs` | None |
| `import userroles` | `export userroles` | None |
| `import outlooktemplates` | `export outlooktemplates` | None |
| `import secureconfigs` | — | `plugin step config set` (see [Plugin step configuration](#plugin-step-configuration)) |

No replacement commands or configuration-file migrations are provided for the retired pairs, and
the legacy JSON formats (`bulkdelete.json`, `queue.json`, `calendar.json`, `slaconfig.json`,
`routingruleconfig.json`, `userrole.json`, `outlooktemplate.json`) are no longer read — including
in custom filenames. Outlook synchronization filters are not Word/Excel document templates.

Retiring these commands does not modify existing Dataverse data: recurring bulk-delete jobs,
queues, calendars, SLAs, routing rules, user-role assignments, and Outlook filters are left
untouched. Review them separately in the environment if their schedules or settings need changing.

The `teamtemplates` and `documenttemplates` transfers are not retired; they moved to their own
command branches and require a new file format (see below).

## Retired maintenance commands

The entire `maintenance` branch is removed without compatibility aliases. All remaining paths fail
with a nonzero exit code and an unknown-command diagnostic:

| Removed command | Removed behavior / configuration | Available replacement |
|---|---|---|
| `maintenance bulkdelete` | One-off FetchXML bulk-delete jobs with `--poll-interval`; recurring `bulkdelete.json` transfers are also retired | None |
| `maintenance autonumber` | Auto-number format overrides from legacy JSON | None |
| `maintenance protectfields` | Environment-wide locking of calculated fields | Column-level protection in `solution copy-components` (see below); no environment-wide equivalent |
| `maintenance carrierinfo` | `carrier.json` export of custom carrier tables | None |
| `maintenance removeredundantcomponents` | Removing components shared between source and target solutions (`--dryrun`, `--includeEntities`) | None |
| `maintenance filterfxplugins` | Updating plugin-step filtering attributes from legacy JSON | None |
| `maintenance ensuresdksteps` | Enabling/disabling plugin steps by solution | `plugin step enable` / `plugin step disable` (see below) |
| `maintenance createworkflowstate` / `maintenance workflowstate` | Capturing/applying workflow state from legacy config | `process init` / `process apply` (see [Process state and ownership](#process-state-and-ownership)) |

No supported migration of these configurations is promised. Updating the CLI does not cancel or
delete jobs, reset auto-number formats or managed properties, change carrier data or solution
memberships, or reset plugin filtering attributes.

### Plugin step enable/disable

`plugin step enable` and `plugin step disable` replace `maintenance ensuresdksteps`:

```bash
# Enable or disable all steps in a solution
dgtp plugin step enable --solution mysolution
dgtp plugin step disable --solution mysolution
```

A step can instead be identified by `--step-id <guid>` or by the composite key `--plugin-type`
`--message` `--stage` `--entity`. Differences from `ensuresdksteps`:

- `--dry-run` is supported; there is no `--confirm` option.
- Steps already in the desired state are skipped and reported as unchanged.
- The solution name is matched exactly (no wildcards); an unknown solution fails.
- `--reason` replaces the step description, and only when the state changes.

## Retired analyze commands

The top-level `analyze` branch is removed without compatibility aliases. The following paths now
fail with a nonzero exit code and an unknown-command diagnostic:

- `analyze entityallassets`
- `analyze noactivelayer`
- `analyze activelayer`
- `analyze toplayer`
- `analyze redundantcomponents`
- `analyze redundantpatches`

No replacement commands or configuration migration are provided, and previously generated reports
under `Analyze/` are not migrated. The retirement does not modify Dataverse data or metadata, and
it does not delete existing local configuration or report files. `solution lint` and the other
`solution` commands are independent features, not replacements for the retired analysis.

## Solution copy-components: calculation-column protection

**Breaking default behavior:** `solution copy-components` now also locks calculation columns, in
addition to copying solution membership. For every copied Calculated, Rollup, or Power Fx Formula
column it sets the column's `IsCustomizable` managed property to `false`. Formulas and unrelated
settings are not changed.

- Scope is the final copy plan: explicitly included attributes plus eligible fields of completely
  copied tables. Managed attributes, simple fields, and skeleton-only tables are not affected.
- The managed property applies to every solution containing the column in the current environment.
  It is a column-level deployment policy, not data-access security; labels and translations may
  remain editable.
- The caller needs the existing copy/cleanup permissions plus permission to update column metadata.

```bash
# Preview the copy and protection plan without writes
dgtp solution copy-components target_solution --source source_a,source_b --dry-run

# Copy, then protect the copied calculation columns
dgtp solution copy-components target_solution --source source_a,source_b

# Bypass protection and ALL best-practice selection rules
dgtp solution copy-components target_solution --source source_a,source_b --raw
```

`--raw` is not a protection-only switch: it also disables managed/active-layer filtering and
preserves complete/non-complete table behavior rather than normalizing it.

Protection starts only after the copy and app cleanup succeed. There is no transaction or
automatic rollback: a failure stops later changes but does not undo earlier ones, and re-running
against an unchanged plan makes no further protection updates. Disabling this policy later does
not restore previous managed properties.

## Team template transfer

The verb-first team-template commands have been removed without aliases:

| Removed command | 3.x replacement |
|---|---|
| `export teamtemplates` | `teamtemplates export <File>` |
| `import teamtemplates` | `teamtemplates import <File>` |

The 2.x transfer file was a bare JSON list and could include system templates. To migrate it:

1. Discard all entries marked `issystem: true` — their GUIDs are protected, and including them
   fails the entire import at preflight.
2. Remove the `issystem` property from the remaining entries.
3. Wrap them in the versioned V1 envelope, preserving each template GUID and logical table name,
   and supply a valid access-rights mask:

```json
{
  "$schema": "https://raw.githubusercontent.com/DIGITALLNature/DigitallPower/main/schemas/teamtemplates/v1/schema.json",
  "schemaVersion": 1,
  "templates": [
    {
      "teamtemplateid": "4e17461c-efec-43a0-835b-08fa78af1f83",
      "entity": "account",
      "teamtemplatename": "Account readers",
      "description": null,
      "defaultaccessrightsmask": 1
    }
  ]
}
```

`defaultaccessrightsmask` is required and must be a non-zero combination of the supported
access-team rights: Read (`1`), Write (`2`), Append (`4`), Append To (`16`), Delete (`65536`),
Share (`262144`), and Assign (`524288`). Create (`32`) is not supported. Names are limited to 100
characters, descriptions to 1,500 characters, and table names must match `^[a-z][a-z0-9_]*$`.
Name duplicates and target collisions are case-insensitive. The legacy bare array is not read
automatically.

Import matches by GUID only: it never adopts a same-name record with a different GUID, and an
existing GUID cannot be reassigned to another table. Conflicts, system-template targets, invalid
rights, and invalid table metadata fail preflight before any writes. Omitted or null descriptions
clear the existing description. Unlisted templates remain unchanged by default.

Use `--overwrite` to replace an existing export file. Export selection uses repeatable
`--table <LogicalName>` options. Cleanup is opt-in: pass both `--cleanup` and one or more
repeatable `--cleanup-table <LogicalName>` options — scope is never inferred from the file or
export filters, and there is no `--all` or global cleanup option. An empty input with cleanup is
rejected. Both commands support `--dry-run`; import validates the full plan without writing,
while export does not create or replace its file. Import is not transactional: mutations stop at
the first failure and completed work is not rolled back; cleanup starts only after all creates and
updates succeed.

## Process state and ownership

The legacy workflow-state commands and their configuration format are removed without aliases:

| Removed command | 3.x replacement |
|---|---|
| `maintenance createworkflowstate --output <File> --solutions <Names>` | `process init <File> --solution <UniqueName>`; repeat `--solution` instead of passing comma-separated names |
| `maintenance workflowstate --config <File>` | `process apply <File>` |

Regenerate the configuration with the new command rather than renaming old properties:

```bash
dgtp process init ./processes.json --solution ContosoCore \
  --capture both --owner-mapping ./owners.source.json
dgtp process apply ./processes.json --owner-mapping ./owners.target.json --dry-run
dgtp process apply ./processes.json --owner-mapping ./owners.target.json
```

Use `--overwrite` explicitly when recapturing an existing file. The new V1 format uses
`schemaVersion: 1` and a `processes` array with a nonempty `processId` GUID and at least one of
`active` or `owner` per entry. See the [process command reference](../../reference/commands/process.md)
and the [V1 schema](../../../schemas/process/v1/schema.json).

| Legacy behavior or setting | 3.x behavior |
|---|---|
| Display-name, unique-name or table-scoped keys | `processId` is the only identity; an optional `name` is ignored for matching. Processes recreated under different IDs require explicit configuration changes. |
| `disabled` flags | Explicit `active` booleans; invert existing intent when migrating. Omitted state is preserved, not activated implicitly. |
| `defaultOwner`, per-process domain names | Portable owner-mapping files and an explicit `owner` key per entry; no most-common-owner default. Users are supported, not teams. |
| `defaultImpersonate` or per-flow impersonation | Run-level `--activate-as <OwnerKey>` or `--activate-as-owner`, mutually exclusive; they apply to activation and deactivation alike. Assignments use the connection identity. |
| `--solutions`, `solutionFilter` | Required repeatable exact `--solution` on init only; apply acts exclusively on the configured IDs. |
| Publisher, wildcard or managed-state selection | Not supported. Capture exact solutions and edit explicit intent instead. |
| `--tablereport`, `--detailed` | Removed; outcomes are always reported. |
| Legacy workflow schema file | `schemas/process/v1/schema.json`; the legacy format is not read. |

Classic workflows, business rules, actions, business process flows, and cloud flows are supported;
dialogs, AI flows, and desktop flows are not. Definitions and connection references are not
deployed.

Review the generated file before applying it. Unlisted processes and omitted properties are
preserved, and owner-only changes preserve activation state. Preflight resolves the full input
before writes, but execution is not atomic: updates continue after failures, and a failed owner
assignment after deactivation triggers one restoration attempt. Inspect the report for partial
effects. Dry-run does not prove privileges or activation dependencies.

## Document templates

The old documenttemplate commands are removed without aliases:

| Removed command | Replacement |
|---|---|
| `import documenttemplates --filedir <Directory> --filename <File>` | `documenttemplates import <Manifest> [--dry-run]` |
| `export documenttemplates --filedir <Directory>` | `documenttemplates export <Directory> [--entity <LogicalName>] [--type word\|excel] [--overwrite]` |

Regenerate packages with the new export command rather than relabeling a legacy manifest. The V1
format requires `schemaVersion: 1` and `templates`; each entry requires `sourceId`, `name`,
`documentType` (`word` or `excel`), `entity`, `file`, `languageCode`, and `description` (string
or explicit null). Legacy `document_status`, `force_update`, `ignore_missing`, snake-case metadata
properties, inline FetchXML filters, and `FORCE`/`MISSING` directives are not parsed.

```bash
dgtp documenttemplates export ./templates --entity account
dgtp documenttemplates import ./templates/documenttemplates.json --dry-run
dgtp documenttemplates import ./templates/documenttemplates.json
```

Matching uses `(name, documentType, entity)` with case-insensitive names. A match preserves its
target ID; a new template uses `sourceId`, and conflicting IDs fail preflight. Names are not
trimmed and extensions are not stripped. Document files must remain inside the manifest directory
(including symlink resolution); there are no search-path fallbacks. Explicit null descriptions
clear the target, and language has no default.

Export includes active templates only; import activates every successfully listed template — this
is active deployment, not draft-preserving backup/restore. Unlisted templates stay unchanged. No
cleanup, implicit deactivation, forced replacement, or delete/recreate is available. Execution is
best-effort and can leave reported partial effects; unknown Word bindings/relationships fail
validation instead of being skipped. Excel content is uploaded as-is.

See the [documenttemplates command reference](../../reference/commands/documenttemplates.md) and
the [V1 schema](../../../schemas/documenttemplates/v1/schema.json).

## Code generation

dgtp 3 supports explicitly versioned V2 code-generation configs only. Unversioned and V1 configs are
rejected; adding `version: 2` and `type` to a V1 file is not a complete migration. V2 uses one
config and one invocation per target. The discriminator is case-sensitive: use lowercase `"type"`
with `"dotnet"` or `"typescript"`. It may appear anywhere in the JSON object; `$schema` annotations
remain supported.

A combined V1 config must be split into one config per target rather than relabeled:

```json
{
  "version": 1,
  "Entities": ["account", "contact"],
  "Solutions": ["ContosoCore"],
  "Actions": ["contoso_ApproveOrder"],
  "GlobalOptionSets": ["contoso_status"],
  "NameSpace": "Contoso.Dataverse.Model",
  "SuppressTypeScript": true
}
```

becomes, for example:

```json
{
  "$schema": "https://raw.githubusercontent.com/DIGITALLNature/DigitallPower/main/schemas/codegeneration/v2/dotnet.schema.json",
  "version": 2,
  "type": "dotnet",
  "namespace": "Contoso.Dataverse.Model",
  "entities": { "names": ["account", "contact"], "fromSolutions": ["ContosoCore"] },
  "requests": ["contoso_ApproveOrder"],
  "optionSets": ["contoso_status"],
  "output": { "include": { "metadata": true } }
}
```

```json
{
  "$schema": "https://raw.githubusercontent.com/DIGITALLNature/DigitallPower/main/schemas/codegeneration/v2/typescript.schema.json",
  "version": 2,
  "type": "typescript",
  "entities": { "names": ["account", "contact"], "fromSolutions": ["ContosoCore"] },
  "requests": ["contoso_ApproveOrder"],
  "optionSets": ["contoso_status"]
}
```

Run each target separately with its own config file:

```powershell
dgtp codegeneration ./generated -c ./genconfig.dotnet.json
dgtp codegeneration ./generated -c ./genconfig.typescript.json
```

Common V1 fields map into the typed V2 configs as follows:

| V1 field or behavior | V2 migration |
|---|---|
| `Entities`, `Solutions`, `EntityMask` | `entities.names`, `entities.fromSolutions`, `entities.mask` |
| `Actions`, `CustomAPIs`, `AdditionalSdkMessages`, `SdkMessageFilters` | Put the request names to generate in `requests`; V2 has no separate SDK-message filter. |
| `GlobalOptionSets` | `optionSets` |
| `NameSpace`, `UseBaseLanguage` | Set `namespace` explicitly for .NET (V2 defaults to `Digitall.Dataverse.Model`; the TypeScript `namespace` field is accepted but unused). Set `language` to an LCID when needed; `language: null` uses the organization base language. |
| `Forms` | `output.forms.filter` in the TypeScript config, using the V2 form identifier format. |
| `SuppressOptions`, `SuppressLogicalNames`, `SuppressContext`, `SuppressRelations`, `SuppressNavigationProperties`, `SuppressEntityTypeCode`, `SuppressAlternateKeys` | For .NET, set the matching `output.include` property to the inverse boolean, e.g. `SuppressContext: true` becomes `output.include.context: false`. For TypeScript, select the option sets to generate through `optionSets`; there is no V1-style suppression flag. |
| `SuppressActions` | Remove Custom API/action names from `requests` to omit their wrappers and requested message constants. For TypeScript, `output.customApis: false` disables wrappers while keeping requested message declarations. .NET has no independent wrapper-suppression switch. |
| `SuppressSdkMessages` | No independent V2 equivalent. .NET always emits SDK message constants, including built-ins, even when `requests` is empty; TypeScript omits message declarations when `requests` is empty. |
| `SuppressMetaData` | Invert to `output.include.metadata`. Note the default changed: V1 generated metadata unless suppressed, while V2 defaults metadata off — set `output.include.metadata: true` when still required. |
| `SuppressDotNet`, `SuppressTypeScript` | Choose which target config(s) to create and invoke; there is no combined generation command. |
| `Virtual`, `EditableReadOnlyProperties`, `OnlyFormsFromSolutions`, `XrmMockFormHelpers` | `output.virtual`, `output.editableReadOnly`, `output.forms.fromSolutions`, `output.forms.testHelpers` in the relevant target config. |
| `SuppressNullableSupport` | Select the .NET target that matches the intended nullable behavior; V2 has no separate nullable-suppression switch. |

V1 `TypescriptGeneratorVersion: "Full"` is removed. Update TypeScript consumers that depend on
Full-only runtime wrappers to the supported ambient/interface output — the former Light output is
the single supported TypeScript pipeline, with no mode selector. `EntityFilters`,
`EntityRefFilters`, and `EntityFormFilters` are rejected without replacement, as are other V1-only
settings such as `Hints`, `TypingPath`, and `BusinessProcessFlows`. The `codegeneration` command,
its `cg` alias, and its options are unchanged.

Before regenerating, back up any custom edits inside generated folders: TypeScript generation
clears the entire `Model/TypeScript` subtree (including old Full-mode files), .NET generation
deletes generated `*.cs` files directly inside `Model/DotNet`, and metadata generation deletes
`*.xml` files directly inside `Model/MetaData`. Files outside those folders are not removed
automatically — inspect and remove obsolete generated files there yourself.

## Connections (replacing profiles)

The `profile` branch is removed, not retained as an alias. Use `connection` instead:

| Removed command | 3.x replacement |
|---|---|
| `profile list` | `connection list` |
| `profile create <name> <url> --msal` | `connection create <name> --url <url>` |
| `profile create <name> <connection-string>` | Recreate a typed connection (below), or pass a one-off connection string to the Dataverse command |
| `profile select <name>` | `connection select <name>` |
| `profile delete <name>` | `connection delete <name>` |
| `profile purge` | `connection delete --all`; add `--yes` to skip confirmation in automation |
| `profile auth-check` | `connection status` |

### Recreate connections after upgrading

**Existing 2.x profiles, saved connections, and cached sign-ins are not imported automatically.**
Before upgrading, record the environment URLs, connection names, and authentication settings you
need (keeping secrets in your existing secret manager). Recreate the connections in 3.x and sign
in again for user connections.

Saved connections live in `connections.json` under the per-user dgtp data directory; `DGTP_HOME`
overrides that directory. Client secrets and PFX passwords are stored separately using the
platform's protected storage. The 2.x profile data is neither imported nor deleted —
`connection delete --all` only deletes the new saved connections and their credentials, not the
old store; remove the old data manually if you want it gone.

Application state also moves to the stable data directory as `state.json`. The 2.x telemetry
identity, notice state, and update-check timestamp are not imported: a new anonymous installation
ID and a one-time telemetry notice are initialized on the first telemetry-enabled command in 3.x.
`DGTP_TELEMETRY_OPTOUT`, `DO_NOT_TRACK`, and `--no-telemetry` suppress this initialization.
Future upgrades reuse this state across major versions.

Creation now uses typed authentication options instead of persisting an arbitrary connection
string:

```powershell
# Interactive user sign-in; --tenant is optional
dgtp connection create dev --url https://contoso.crm4.dynamics.com

# User sign-in without a browser on the machine running dgtp
dgtp connection create dev-device --url https://contoso.crm4.dynamics.com --device-code

# Service principal; supply the secret through your secret-management tooling
dgtp connection create prod --url https://contoso.crm4.dynamics.com --tenant <tenant-id> --client-id <client-id> --client-secret <secret>

# Select the recreated connection and check authentication
dgtp connection select dev
dgtp connection status
```

Certificate and Azure DevOps federated connections are also supported — see the
[authentication types reference](../../reference/commands/connection.md#authentication-types).
Secrets passed on the command line can be exposed in process arguments, shell history, and
pipeline logs; use secret masking and avoid echoing these commands.

Update existing creation scripts, including scripts already using the `connection` branch:

| Old option or behavior | 3.x replacement |
|---|---|
| Positional URL/connection string in `profile create` | `connection create <name> --url <url>` plus the appropriate authentication options |
| `profile create --msal` | Interactive sign-in is the default; use `--device-code` when needed |
| `profile create --skipcheck` | `connection create --no-verify` — skips the Dataverse connectivity check, not user sign-in |
| `connection create --connection-string <string>` | Use typed authentication options, or pass the string to the Dataverse command without saving it |
| `connection create --application-id <id>` for Azure DevOps federation | `--client-id <id>` |
| `--insecure` / `--security-protocol` | Removed; configure certificate trust and TLS through the OS/runtime instead |

`connection status` attempts token acquisition without interactive sign-in; it does not check
Dataverse permissions or connectivity. It exits `0` if a token is acquired and `2` if authentication
is required or fails. `connection refresh` reauthenticates interactive/device-code connections
only; it does not rotate service-principal credentials.

### Invocation options and configuration

Replace `--profile <name>` with `--connection <name>` on Dataverse commands:

```powershell
dgtp documenttemplates export ./templates --connection dev
```

Set `DGTP_CONNECTION` to select a named connection for one invocation, or use the saved selection
from `connection select`. For authentication modes outside the saved types, pass
`--connection-string <string>` to the Dataverse command or set `DGTP_CONNECTION_STRING`; these
strings are never persisted. Prefer the environment variable for secret-bearing strings:

```powershell
# Populate this variable from your secret manager, not a committed script
$env:DGTP_CONNECTION_STRING = "<Dataverse connection string>"
dgtp documenttemplates export ./templates
Remove-Item Env:\DGTP_CONNECTION_STRING
```

Command-line options override their corresponding environment variables, and an ad-hoc connection
string takes precedence over a named connection, including one supplied with `--connection`.

The global `dgtp.json` configuration file and `dgtp:*` environment-variable binding are removed:

| Legacy setting | 3.x replacement |
|---|---|
| `profile` / `dgtp:profile` | `--connection` / `DGTP_CONNECTION` |
| `xrm` connection-string settings / `dgtp:xrm:*` | Typed saved connections, or `--connection-string` / `DGTP_CONNECTION_STRING` |
| `pollrate` (milliseconds) | Removed without replacement together with `maintenance bulkdelete` |
| `DGT_TELEMETRY_OPTOUT` | `DGTP_TELEMETRY_OPTOUT` or `DO_NOT_TRACK` |

Command-specific configuration files remain supported. Review the
[configuration reference](../../reference/configuration.md) for the supported environment
variables, including `DGTP_NON_INTERACTIVE` for unattended execution.

## Plugin deployments

Replace `dgtp push <assembly-or-package>` with `dgtp plugin push <assembly-or-package>`:

```bash
dgtp plugin push ./bin/Release/MyPlugin.dll --solution mysolution
dgtp plugin push ./bin/Release/MyPlugin.1.0.0.nupkg --publisher-prefix contoso --solution mysolution
```

Before migrating deployments, account for these differences:

- `plugin push` requires declarative registration attributes from
  `Digitall.Plugins.Registration` 3.0.0 or later; older registration namespaces are not
  recognized. Assemblies with manually maintained registrations must add supported attributes or
  stay on dgtp 2.x.
- Workflow activities (`CodeActivity`) are not supported by `plugin push`. Keep those deployments
  on dgtp 2.x until they are replaced with a supported plugin or Custom API design.
- `--delete-on-upgrade` and `--no-migrate-custom-apis` are removed. For standalone assembly
  major/minor version changes, `plugin push` creates a replacement assembly, migrates matching
  declared plugin steps, and removes the superseded assembly and registrations. Review the plan
  with `--dry-run` before deploying.
- `--publish` is not needed; plugin registration takes effect immediately.
- `.nupkg` targets require `--publisher-prefix`; DLL-only targets do not.
- The target may also be a glob pattern. The whole batch is validated before any write: duplicate
  declarations across targets, unreadable artifacts, a target matching no files, or files without
  plugins fail the run.
- `--confirm` prompts before applying each target plan in interactive sessions. Non-interactive and
  CI runs do not prompt, so review the plan and deployment permissions before using the command in
  automation.

### Custom data providers

Data-provider deployment has **experimental support** — validate the migration in a non-production
environment first. Upgrade `Digitall.Plugins.Registration` to 3.0.0 or later and update the
provider declarations to the new constructor that takes the configuration-table schema name and
explicit provider name (use the schema name, not the business virtual-table name; changing this key
identifies a different provider). See the
[registration library](https://github.com/DIGITALLNature/DigitallRegistrationPower) for details.

`plugin push` deploys the provider record instead of ordinary plugin steps. The configuration
table must already exist in the target environment; it is not created or added to the solution.
Obsolete manually created step registrations are not deleted automatically — review and remove
them separately. See [deployment scope](../../reference/commands/plugin.md#custom-data-providers)
for what is and is not provisioned.

### Plugin step configuration

`import secureconfigs` is removed. The legacy JSON identified a step by display name and supplied
its secure value:

```json
{
  "plugin_step": "<plugin step display name>",
  "secure_config": "<secret value>"
}
```

There is no automatic conversion. Configure each step individually in the target environment with
`plugin step config set`, identifying the step by its Dataverse step ID or by the complete
composite key (`--plugin-type`, `--message`, `--stage`, `--entity`) — a display name does not
uniquely identify a step. For multiple steps, script one invocation per step.

```powershell
# File-based value: the file contains only the secure text, not the old JSON envelope
dgtp plugin step config set --step-id <step-guid> --secure-file .\secure-value.txt

# Composite key or inline value
dgtp plugin step config set --plugin-type Contoso.Plugins.Sample --message Update --stage PreOperation --entity account --secure-file .\secure-value.txt
dgtp plugin step config set --step-id <step-guid> --secure "<value-from-secret-manager>"
```

`--secure ""` explicitly clears the secure configuration; omitting `--secure` and `--secure-file`
leaves it unchanged. The unsecure equivalents are `--unsecure` and `--unsecure-file`. Inline
values may be exposed in process arguments, shell history, or logs — prefer a protected secret
file and do not commit it. The legacy `--filedir`, `--filename`, and `--inline` inputs do not
apply here.

### Managed identities

`plugin push` does not provision or bind managed identities. Remove managed-identity declarations
from plugin assemblies and configure the Dataverse identity record, assembly/package binding,
Entra federated credential, and permissions through each environment's provisioning pipeline
instead. Existing bindings are left untouched during updates, but a replacement assembly does not
inherit the superseded assembly's binding and needs separate provisioning.

## Webresource deployments

Replace `dgtp push <directory>` with `dgtp webresource push <directory>`:

```bash
dgtp webresource push ./webresources --publisher-prefix contoso --solution mysolution
```

The command options and validation differ from the combined command:

| 2.x behavior or option | 3.x behavior |
|---|---|
| `--config <file>` for webresource name mappings | `--mapping-file <file>` |
| Derive directory names from the target solution | Pass `--publisher-prefix` explicitly for a directory target |
| Push one webresource file by itself | Pass `--name <logical-name>`; `--publisher-prefix` is not needed for a single file |
| `--publish` | Changed webresources are published automatically |
| `--delete-obsolete` | Requires a directory target and `--solution`; an empty directory is a no-op and cannot delete every resource in the solution |

The mapping file remains JSON: keys are paths relative to the target directory, values are
Dataverse logical names. See the [webresource command reference](../../reference/commands/webresource.md)
for the complete option reference and mapping examples.

## Rollout checklist

1. Record the 2.x connections and authentication settings needed for your environments, then
   recreate and select typed connections in 3.x.
2. Replace `profile` commands, `--profile`, legacy creation options, and global configuration
   bindings in scripts and pipelines. Verify a non-production Dataverse command — not just
   `connection status` — before switching production automation.
3. Inventory scripts and pipelines that invoke `dgtp push` (target type and options), then move
   each deployment to its resource-specific command.
4. Identify workflow activities and assemblies without supported declarative registrations; these
   need a design change or must remain on dgtp 2.x.
5. Update option names and supply the required publisher prefix for plugin packages and webresource
   directories.
6. Run the replacement deployment commands with `--dry-run`, inspect the plan, and validate in a
   non-production environment before switching production automation to 3.x.
7. Keep the approved dgtp 2.x version available for rollback until the migrated connections and
   deployments have been verified.
